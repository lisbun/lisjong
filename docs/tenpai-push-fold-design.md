# 単独リーチ下の聴牌PUSH/FOLD（H2）— 設計

Issue: [#254](https://github.com/lisbun/lisjong/issues/254)（親: lisbun/lisjong-project#84、前段: #236・#249）

他家1人がリーチ中で、自分が未リーチ・聴牌を保てる打牌判断について、押す打牌と降りる打牌を
同じ単位で比べる候補の設計である。**実装・対局実行・seed予約はまだ行っていない。**
Championは書き換えない。本書の式・表・候補は設計案であり、強さや判断の質の主張ではない。

## 1. 現行経路（Championが聴牌時にしていること）

`PlacementAwareSpeedCallPolicy`の判断順は、継承元を含めて次のとおり（lisjong `c3f12ba`で確認）。

| 順 | 条件 | 行動 | 実装 |
|---|---|---|---|
| 1 | ロン・ツモが合法 | 和了する | `TwoStepUkeirePolicy._decide` |
| 2 | `RiichiAction`が合法 | 必ずリーチする（Always Riichi）。他家リーチの有無・待ち・打点を見ない | `_choose_riichi` |
| 3 | 打牌 | 下の打牌経路 | `_decide_discard` |
| 4 | 鳴き・槓・Pass | 他家リーチ中は役確定型スピード鳴きをしない。聴牌時の役牌鳴きは向聴が下がらないので起きない | `_decide` |

打牌経路（3）で、他家リーチがあるときの分類は`_decide_push_fold()`だけが決める。

```text
PUSH  合法打牌のどれかが、打牌後の構造的向聴 0（聴牌）を保てる
FOLD  それ以外
```

- PUSHでは、**全合法打牌**を攻撃評価（FH completion mass → 手牌価値）へ渡す。リーチ者への危険度・現物は
  一切見ない。打点・待ちの残り枚数・巡目・点数状況も、押すかどうかには使わない
- 向聴は構造だけで判定し、役の有無を見ない。役のない副露聴牌（形式聴牌）もPUSHになる
- 副露手で役牌の確保がなく、副露がタンヤオ・一色のrouteと両立する場合だけ、PUSHのとき
  `_route_preserving_actions()`がroute向聴最小の打牌へ絞る
- `ALL_LAST_TOP_SPEED`の事前守備（`_top_fold_actions`）はFOLDのときだけ働く。聴牌PUSHには作用しない
- 2向聴以上のmechanism守備（#163）は、打牌後最小向聴が2未満なら発動しない

したがって「単独リーチ・自分未リーチ・聴牌」の判断は、Championでは次の3つに分かれる。

| 区分 | 条件 | Championの行動 |
|---|---|---|
| (A) 追っかけリーチ | 門前で`RiichiAction`が合法 | 常にリーチ。その後の打牌は自分が`DECLARED`なので「未リーチ」ではない |
| (B) 門前・リーチ不可 | 持ち点不足、残りツモなし等で`RiichiAction`が合法でない | PUSH打牌 |
| (C) 副露聴牌 | 暗槓以外の副露がある | PUSH打牌（役なしを含む） |

## 2. 対象ゲート（初版）

初版が変えるのは **(B)(C)の打牌判断だけ**とする。(A)のリーチ宣言は変えない（理由は「対象外」）。

候補は`PlacementAwareSpeedCallPolicy`をexact parentとし、`_decide_discard()`だけをoverrideする。
まずChampionの打牌 C0（`super()._decide_discard()`の結果）を求め、次が**すべて**成り立つときだけ比較へ進む。
1つでも外れたらC0の`PolicyDecision`をそのまま返す。

1. 自分が`RiichiState.NONE`
2. `ron_legal_estimator.in_riichi_scope()`が真（他家のちょうど1人が`DECLARED`/`ACCEPTED`で、その席に打牌がある）
3. 南4局以降（`_is_all_last()`）ではない
4. 合法打牌が2牌種以上
5. Championの役保持filter後の集合で、分類が`PUSH`
6. C0が聴牌を保つ（打牌後の構造的向聴が0）
7. C0後の待ちに、自分から見て残り1枚以上の牌種がある
8. 4節の表に、この判断のbucketの値がある

- 和了・リーチ・鳴き・槓・Passは継承し、変えない。優先順位は1節の表のまま（和了 > リーチ > 打牌）
- 門前／副露は区別せず同じ式で扱う。違いは自手の和了点（役の有無・門前ツモ）に現れる
- 現物の有無はゲート条件にしない。現物は降りる候補の選択（3節）で危険度0として扱われる
- 3を置くのは、オーラスでは局収支より順位の比重が大きく、点数だけの比較が成り立ちにくいため。
  オーラスの点数状況modeはChampionの処理を優先する
- 途中の打牌が替われば、その後の手牌・鳴き機会は変わる。対象外の判断が同じ入力で同じ出力になるという意味である

### 推定不能時の扱い

| 状況 | 扱い |
|---|---|
| 待ちモデル（`selection.json`）のSHA-256・特徴量セットが登録値と違う、表のidentityが違う | 構築時にエラー。別モデル・別表へ黙って替えない |
| native拡張（`evaluate_win`）が使えない、`SCORING_API_VERSION`が違う | 構築時にエラー。Championと同じ挙動へ黙って落とさない |
| 推定器が`None`（提供範囲外） | ゲート2で外れているのでC0 |
| 表のbucketが未提供（support不足で事前登録時に除外） | ゲート8で外れるのでC0 |
| 判断中の`ValueError`（牌枚数の不整合等） | 握りつぶさずに送出する |

## 3. 押す候補・降りる候補・選択

- **押す候補** `a_push` = C0
- **降りる候補** `a_fold` = 全合法打牌（役保持filter前）のうち、リーチ者へのロン合法確率 `p(a)` が最小の打牌。
  同値は、打牌後の向聴が小さい順 → 受け入れ枚数が多い順 → canonicalな打牌順（`discard_action_sort_key`）
- `p(a_fold) >= p(C0)` ならC0を維持する（より安全な牌がない）
- それ以外は 4節の `V` を2候補について計算し、**`V(a_fold) > V(C0)` のときだけ `a_fold` を選ぶ**。
  同点はC0。margin・閾値の調整項は置かない
- `a_fold`が聴牌を保つ場合（安全牌で聴牌維持）も同じ式で比べる。このとき両方に聴牌側の継続価値を使う

比較するのは2候補だけにする。全打牌の順位付けはしない（計算時間と、表の外挿を増やさないため）。

## 4. 比較式

**単位は点（その局の自分の収支。供託・本場を含む）、時間範囲は現在の局の終了まで。**
次局以降・順位・ウマオカは式に入れない（仮定A6）。

```text
V(a) = − p(a) · L  +  (1 − p(a)) · C(a)

C(a) = q_ron(s) · G_ron(a) + q_tsumo(s) · G_tsumo(a) + R_T(s)     a が聴牌を保つ
     = R_F(s)                                                      a が聴牌を崩す
```

| 記号 | 意味 | 求め方 | 現状 |
|---|---|---|---|
| `p(a)` | 打牌 `a` の牌種が、リーチ者にとって**ロン合法**である確率 | `estimate_riichi_ron_legal_belief()`（#245の凍結モデル × `certain-ron-illegal-zero-v1`）の`ron_legal_probability` | あり（#277段階1） |
| `L` | この打牌で放銃したときの支出 | リーチ者が親か子かの2値の表（リーチ者のロン和了点の平均）＋ 本場×300 | **なし** |
| `G_ron(a)` / `G_tsumo(a)` | 自分が和了したときの収入 | `a`後の待ち牌種ごとに`evaluate_win()`でロン・ツモの受取点を計算し、自分から見た残り枚数で加重平均。役なしの牌種は0点・0枚として扱う。＋ 供託×1000 ＋ 本場×300 | 計算器あり（#263）。加重平均は新規 |
| `q_ron(s)` / `q_tsumo(s)` | 今の打牌が通った後、局の終了までに自分がロン／ツモで和了する割合 | 5節のsourceのtrainでbucketごとに数える | **なし** |
| `R_T(s)` | 聴牌を保って今の打牌が通った後の、**自分の和了以外**による収支の平均（後の放銃、ツモられ、流局時の聴牌料、他家間の和了） | 同上（和了した局は0として平均） | **なし** |
| `R_F(s)` | 聴牌を崩して今の打牌が通った後の収支の平均 | 同上（降りた側の記録） | **なし** |

bucket `s` は次の公開情報だけで決める（境界は事前登録時に、trainの**件数だけ**を見て固定する）。

- 残りツモ山（`live_wall_tiles_remaining`）: 3区分
- 待ちの残り枚数（役がある牌種だけを数える。`q_ron`はロンで役がある枚数、`q_tsumo`はツモで役がある枚数）: 3区分。0枚なら `q = 0`
- `R_F`は残りツモ山の3区分だけ

自分のフリテンは次のように扱う。`PolicyInput`は`own_furiten`を持たないので、公開情報から導出できる分だけを使う。

- 捨て牌フリテン: `a`後の待ち牌種が自分の河（`a`自身を含む）にあれば、ロンの枚数を0、`G_ron = 0`とする。ツモは変えない
- 見逃しフリテン: 候補は和了が合法なら必ず和了する（1節の順1を継承）ので、自分の選択では生じない。
  頭ハネで和了できなかった場合は見逃しではない（engineの規則。[ロン合法確率の設計](ron-legal-belief.md)の照合表）

自手の価値は`G`で局面ごとに正確に計算し、表は確率と残余収支だけを持つ。親子は`G`（正確）と`L`（2値）に反映する。

### 区別する量

| 量 | 本書での扱い |
|---|---|
| 構造的待ち確率（#245） | そのままは使わない。`p`の材料 |
| ロン合法確率（#262・#277） | `p(a)`そのもの |
| 放銃確率 | `p(a)`を、仮定A1・A2の下で読み替えたもの。**校正済みの放銃確率とは呼ばない** |
| 放銃時の点数 | `L`。牌・巡目によらない平均（仮定A3） |

`V`は表と仮定に依存する**比較用の値**であり、期待収支とは呼ばない。5節の対比較で、`V(a_fold) − V(C0)`の
符号・大きさが実測の局収支差と合うかを確認できた範囲でだけ、近似として扱う。

### 仮定（省略する項目）

| | 仮定 | 向き |
|---|---|---|
| A1 | リーチ者は合法なら必ずロンする | 相手がChampion系なら成り立つ（和了優先）。見逃す相手では放銃を過大評価 |
| A2 | リーチ者以外の2人へのロン（ダマ・副露）は今の打牌の比較に入れない。後の巡目の分は`R_T`/`R_F`に実測で入る | 押す側・降りる側の両方で過小評価。差への影響は不明 |
| A3 | `L`は牌種・巡目・ドラによらない | ドラ・ドラそばを切る放銃を過小評価 |
| A4 | 継続の方針はChampion（今回の1打だけ替える）。候補自身が後の巡目で再び降りる効果は表に入らない | 押す側の後の放銃を過大に見る可能性 |
| A5 | 表はChampion同士の対局で作る。相手が違えば`q`・`R`は変わる | 別相手構成の評価で確認する |
| A6 | 次局以降・順位・ウマオカは入れない。オーラスは対象外にする | トップ目・ラス目で点数と順位の価値がずれる |
| A7 | `p`の校正は#277の提供行全体（34牌種）での値で、**ゲート判断の候補牌に限った校正は未確認** | 5節で確認する |

### 既存推定器で足りるか

| 必要な量 | 判定 |
|---|---|
| `p(a)` | 足りる（単独リーチ・自分未リーチの範囲で提供。#277段階1でbaselineより良いことを確認済み）。A7の確認が残る |
| `G` | 足りる。聴牌なので完成形を列挙でき、未リーチなので裏ドラは「なし」を明示して完全な点数計算ができる |
| `L` | 足りない。リーチ者の打点推定器はない。初版は2値の平均表で代用し、牌別・巡目別の推定は別の依存作業とする |
| `q`・`R_T` | 足りない。FH completion massは3巡以内の自摸だけの構造的完成率で、ロン・他家の和了・流局を含む和了確率ではない |
| `R_F` | 足りない。Championは聴牌から降りないので、既存の対局記録に該当する局面がない |

入力は`PolicyInput`だけ。表・モデルは学習用sourceから作るが、推論側moduleは正解系module
（`riichi_deal_in_source`・`exact_wait_ground_truth`の正解経路・`ron_legal_ground_truth`等）をimportしない。
自手の待ちは自分の手牌から計算するので隠し情報ではない。

## 5. 依存作業: 同じ局面からの押す／降りる対比較source

`q`・`R_T`・`R_F`・`L`と、A7の確認、そして**そもそも降りた方が良い局面があるか**を、1つのsourceで測る。

- 対局は決定的なので、同じseed・同じ席配置なら、判断が同じ間は同一に進む
- 対照: Champion×4の半荘。ゲート判断（2節の1〜7）を通し番号で記録する
- 降りる側: 対照の k 番目のゲート判断**だけ**で`a_fold`を切り、それ以外はChampionのまま進める。
  その局の終了まで実行すれば足りる
- 1つのゲート判断につき、同じ局面からの「押す（C0）」「降りる（`a_fold`）」の局収支・結果
  （和了の方法と点、放銃と点、流局時聴牌、今の打牌が通ったか）が対で得られる
- `p(a_fold) >= p(C0)`の判断は降りる候補がないので、押す側だけを記録する

これは**同じ局面からの比較**であり、半荘全体の強さの評価ではない（6節と区別する）。

| 役割 | 担当 | 内容 |
|---|---|---|
| ゲート判定・`a_fold`の選択・k番目だけ替えるPolicy・sourceの読み込みと表のfit | lisjong | ゲートと候補選択は、後の候補Policyと同じ関数を使う |
| 対局の実行・記録 | lisjong-arena | engine上の実行、seed予約、記録のdigest |

手順（数・seedは事前登録で固定する。ここでは決めない）:

1. **件数の確認（新しい対局なし）**: 消費済みの開発source（#237 S1、931200..931399の`decisions.jsonl`）で、
   ゲート判断の件数を(B)(C)別・役の有無別に数える（役の判定にnativeが要るのでWSLで行う）。
   結果は規模の見積りにだけ使う
2. seed単位でtrain / validに分ける。trainで表を作り、bucketの境界・support不足で除外するbucketを固定する
3. validで次を報告する（区間は半荘単位のbootstrap）
   - 降りる − 押す の局収支差の平均（全体、bucket別、(B)(C)別、役の有無別）
   - `V(a_fold) − V(C0)`の符号と、実測の局収支差の対応（`V`が降りると判定した判断だけの平均差）
   - ゲート判断の候補牌での`p`の校正（予測の区分ごとの実測放銃率）
4. **中止の条件（事前に固定）**: validで、`V`が降りると判定した判断の局収支差の平均が0以下なら、
   候補の実装・半荘評価へ進まない。結果を記録して設計へ戻る

## 6. 評価計画（候補の開発比較）

5節を通過した場合だけ行う。Championをexact parentとする実験候補で比べ、Champion本体は変えない。

### 境界テスト（focused test）

- ゲートの各条件（1〜8）の内と外。外ではChampionの`PolicyDecision`と一致すること
- (A)で`RiichiAction`を選ぶこと、和了を選ぶことが変わらないこと
- `V`の境界: `V(a_fold) == V(C0)`でC0、わずかに上回ると`a_fold`。`p(a_fold) >= p(C0)`でC0
- 役なし副露聴牌で`G = 0`、門前でツモだけ役がある場合の`G_ron = 0`
- 待ち牌種が自分の河にある場合・`a`自身が待ち牌種の場合に、ロンの枚数が0になること
- `a_fold`が聴牌を保つ場合に聴牌側の式を使うこと、同値時の選択順、赤5・手出し/ツモ切りのaction identity
- 情報境界: 推論側moduleが正解系moduleをimportしないこと、Policy instanceが判断をまたぐ状態を持たないこと
- モデル・表のhash不一致、native未導入で構築が失敗すること

### 開発比較

#249と同じ枠組みを使う（lisjong-engine上、Rust backend、WSL。設計段階ではAWS実行を開始しない）。

| 項目 | 固定する内容 |
|---|---|
| 候補 | 3・4節の1つだけ。表は5節のtrainで作ったもの。結果を見て式・bucket・表を変えない。変えるなら別候補として新seed |
| 対照 | Champion×4。候補は席k＝0〜3に1人（他3人はChampion） |
| 別相手構成 | 相手3人を前Champion（`TargetedHonorReleaseTerminalProgressionPolicy`）にした同じ比較（A5の確認） |
| seed | **事前登録時にlive台帳（arena `seed-registry` branch）と既使用範囲を照合して決める。** 931000..931999は#385のallocation（RETIRED）で、931000..931549は開発比較・学習に使用済み。#245正式test（932000..932099）、5節のsource、推定器の学習・選択seedと重ねない。表の調整に#245正式testを使わない |
| 規模 | 5節1の件数から、打牌が替わる半荘数の見込みを出して決める。この設計では推測しない |
| 事前登録 | seed・規模・相手構成・lisjong/engine/arenaのrevision・wheelとモデル・表のhash・採否規則を、実行前に後続Issueへ記録する |

指標（放銃だけで決めない）:

1. ゲート判断: 件数、`a_fold`を選んだ数、放銃件数・支出（リーチ者宛て／全相手）、和了、流局時聴牌
2. 最初に打牌を替えた局: 同じseed・席の対照の同じ局と対にした局収支差（同じ局面からの比較はここまで）
3. 全局: 和了率・放銃率・流局聴牌率・局収支、順位分布
4. D(s): ［候補席の成績 − 対照の同じ席の成績］の4席平均（返し30,000、ウマ30/10/−10/−30、オカ20）。
   seedを単位に平均と95%記述区間
5. 推論時間（下）

採否（#249に倣う。区間は記述用で、0を含むかどうかでは決めない）:

- 仕組みが働いていない: `a_fold`を選んだ判断が0、またはゲート判断の放銃支出が対照以上
- 通過: 最初に打牌を替えた局の局収支差の平均が0以上、かつ主比較と別相手構成の両方でDの平均が0以上
- 通過しても、正式な強さの証明・Champion昇格の根拠にはしない。正式な判定は未使用seedでのArena評価を別に行う

### 計算時間

- 実戦制限の出典: lisjong-arena `docs/riichilab-client.md`「`request_action.time`の意味とlocal cutoff」。
  serverの期限は`grace_ms + bank_ms`（実traceの例 3000 + 15000）、clientは0.5秒手前で打ち切る。
  **これは実traceの観測であり、RiichiLabの公式仕様としての値は未確認。** 事前登録の前に出典を確認する
- 候補が足す計算は、ゲート判断だけで、34牌種のlogistic 1回と、2候補 × 待ち牌種 × ロン/ツモの`evaluate_win()`
- 予算（案）: ゲート判断での**Championからの増分**が p95 0.1秒以下・最大0.5秒以下。
  Championの観測最大値に収まることだけでは適合としない。増分とゲート判断の絶対値（p50/p95/max）を両方報告する
