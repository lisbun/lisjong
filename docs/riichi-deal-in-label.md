# 単独リーチ者に対する放銃確率推定器 — 定義（S1）

lisbun/lisjong#237（親: lisbun/lisjong-project#84 R1800ロードマップ、H/L共通部品 S1）の
定義部分を記録する。推定器本体・データ生成・評価は後続で扱い、本書が現時点の正本である。

## 位置付け

他家1人がリーチしている局面で、自分の打牌候補ごとに「その牌でリーチ者に放銃する確率」を
推定する部品。H2（価値に応じた押し引き）と学習トラックの入力・補助タスクで使う予定で、
現時点ではどのPolicyにも組み込んでいない。

推定精度、判断の質、強さは別々の主張として扱う。

## 対象局面

- 他家の**単独**リーチ（リーチ成立後）
- 対象外: 複数リーチ、リーチしていない聴牌者（ダマ・副露）

学習・評価データの対象範囲（`SCOPE`、2026-10-03に固定）はさらに狭く、
**他家1人がリーチ中（宣言済みを含む）・自分は非リーチ・候補牌種2以上の打牌判断**とする。
H1/H2向けの初期データとして合理的だが、上記「他家単独リーチ」全体より狭いことを
学習・評価結果の記載でも明記する。

## 推定器の入力

- そのプレイヤーが判断時点で観測できる情報に限る。**自分の手牌を含む**
- 他家の手牌、山、王牌などの隠し情報は入力に使わない

## ラベル

主対象はラベルA、ラベルBは検証用の補助とする。

### ラベルA（ロン可能性）

判断時点で、リーチ者がその牌種でロンできるか。実装は
`lisjong.belief.riichi_ron_label.riichi_ron_label()`。

```text
ron_tile_types = wait_tile_types   if not furiten
               = ∅                 if furiten
```

| 要素 | 定義 |
|---|---|
| 構造的な待ち | 既存の `exact_wait_ground_truth.exact_hand_belief_with_waits()` で `wait_probability > 0` の牌種。待ちの判定は再実装しない |
| 役 | リーチ者はリーチ役を持つため、役なしは生じない |
| 捨て牌フリテン | リーチ者自身のこの局の捨て牌（鳴かれた牌を含む）に待ちの牌種があれば、すべての待ちでロンできない |
| リーチ後の見逃しフリテン | リーチ宣言打牌より後に、和了できた牌（他家の打牌・加槓牌・自摸牌）を和了しなかった場合、以後すべての待ちでロンできない |
| 赤5 | 牌種（`TileType`）で判定し、赤と通常を区別しない |

- 見逃した牌の特定（`passed_tile_types`）は、ラベルを作るデータ経路の責務とする
- リーチ者の手牌に待ちがない入力は、データ不整合として `ValueError` にする

### ラベルB（実際のロン）

その牌を実際に切ったときにロンされたか。選んだ打牌についてしか観測できないため、
ラベルAの検証にだけ使う。対局結果から求め、ラベルAの関数では扱わない。

## 情報境界

- ラベルA/Bはtraining-only truthであり、推定器・Policyの推論入力へ渡さない
- 推論時の入力に隠し情報が入らないことは、推定器を実装する段階でtestで固定する

## データの入力契約（`lisjong.learning.riichi_deal_in_source`）

lisjong-arenaが対局を実行して**観測事実**を記録し、lisjongがこの契約で読み込んでラベルを計算する。
lisjongはArenaのmoduleをimportしない。

| file | schema | 内容 | 読む経路 |
|---|---|---|---|
| `manifest.json` | `lisjong-riichi-deal-in-source-manifest-v1` | 対象範囲、producerのrevision、seedの分割、各fileのbytes・SHA-256・行数 | 両方 |
| `decisions.jsonl` | `lisjong-riichi-deal-in-decision-record-v1` | player-safeな判断（`PolicyInput`・合法手・選んだ打牌） | `read_decisions()`（推論入力の経路。ラベルのfileを開かない） |
| `label_facts.jsonl` | `lisjong-riichi-deal-in-label-fact-record-v1` | 学習専用の観測事実（リーチ者の13枚相当の手牌、リーチ宣言打牌の時点、和了の選択肢が提示された時点・対象牌・選んだ行動、選んだ打牌への提示・放銃） | `read_labelled_source()`（学習専用） |

- 2つの記録は`DecisionKey`（seed、半荘内の判断の通し番号、席）で結合する。キーの欠落・重複・不一致はエラー
- フリテンとラベルAは、記録された事実からlisjongが計算する（河は判断記録の`PolicyInput`から取る）
- 時点の検査: リーチ者の手牌はリーチ宣言打牌以後かつ対象判断より前、和了の選択肢はリーチ宣言打牌より後かつ対象判断より前でなければエラー
- engineとの照合: 選んだ打牌について、ラベルAとリーチ者へのRonActionの提示が一致しなければエラー。選ばなかった候補には照合値を持たせない
- 各行は正準JSONで、`PolicyInput`・行動の射影は`lisjong.learning._typed_values`と一致しなければエラー

## データ分割と評価の使い方（2026-10-03に固定）

- seed（半荘）単位で train / valid / test に分け、manifestに明示する（同じseedを複数の分割に入れない）
- 最初の比較規模は合計200半荘（新しい開発用seedで 160 / 20 / 20）
- trainで学習し、validで確率の校正とモデル選択を行い、testは選択後に1回だけ使う
- 候補（判断 × 候補牌種）を独立な標本とは扱わず、半荘単位でもばらつきを確認する
- 生成経路の検査に使った40半荘（seeds 931100..931139）は、評価に使わない

## ベースライン・推定器・比較手順

推論側は`lisjong.learning.riichi_deal_in_estimator`（`PolicyInput`と候補牌種だけを入力にする。
`riichi_deal_in_source`・待ち判定・リーチ者の手牌を参照しない）、学習・比較は
`lisjong.learning.riichi_deal_in_evaluation`が持つ。どちらもML runtimeに依存しない。

| モデル | 定義 | 当てはめ |
|---|---|---|
| ベースライン1 | 現物（リーチ者の捨て牌の牌種）=0、それ以外は一定値 | validの非現物候補の正例率 |
| ベースライン2 | 既存の古典的危険度score（`_classical_riichi_danger_score`）をlogistic（Platt）で確率へ校正 | valid |
| 推定器 | 構造的に安全な牌=0、それ以外は特徴（古典的危険度scoreの数値と区分、牌の分類×筋、残り枚数、形の成立可能性、ドラ、リーチ者の巡目）のlogistic回帰（`riichi-deal-in-features-v3`） | train。L2強度はvalidのlog lossで選ぶ |

- 構造的に安全な牌: 現物と、リーチ者の最後の打牌より後に他家が切った牌種。後者はリーチ宣言打牌以後に
  出た牌なので、待ちなら見逃しフリテンになり、ラベルAは定義上必ず偽になる。評価時に正例が確率0なら
  エラーにする
- 指標: 候補単位のlog loss・Brier・校正表、判断内の順位付け（正例と負例を両方含む判断のAUC、
  最も安全と推定した牌がロン牌である率）、牌の分類・巡目・残り枚数・構造的安全の別
- 手順: `select`がtrain/validだけで当てはめ・選択を行って結果を書き出し、`test`はその選択を固定して
  testで1回だけ評価する（出力は上書きしない。選択と異なるsourceは拒否する）
- 推定器・ベースライン1とベースライン2の差は、半荘を単位にしたbootstrap（2,000回、固定seed）で
  ばらつきを示す

## 200半荘での比較結果（2026-10-03）

データ: seeds 931200..931399（train 160 / valid 20 / test 20）、Policy `PlacementAwareSpeedCallPolicy`、
producer lisjong-arena `ca92451`・lisjong `f6e0f0c`・lisjong-engine `8735e89`。
判断 train 18,014 / valid 2,415 / test 2,150、候補 189,661 / 25,298 / 22,139、
ラベルA正例 12,954 / 1,675 / 1,512。manifest SHA-256 `e1a6f65e…d05b`。

testの結果（選択を固定して1回だけ評価。推定器は`riichi-deal-in-features-v3`、L2=100）:

| モデル | log loss | Brier | 判断内AUC | 最安全と推定した牌がロン牌の率 |
|---|---|---|---|---|
| ベースライン1（現物=0・一定） | 0.2414 | 0.06309 | 0.554 | 2.59% |
| ベースライン2（古典的score・Platt） | 0.2378 | 0.06271 | 0.685 | 0.43% |
| 推定器 | 0.2313 | 0.06186 | 0.684 | 0.65% |

- 推定器 − ベースライン2（半荘単位bootstrap、95%区間）: log loss −0.0065（−0.0102 〜 −0.0033）、
  Brier −0.00085（−0.00141 〜 −0.00033）。この差には、推定器だけに加えた「構造的に安全な牌=0」の
  効果が含まれる（下の事後分析で分離）
- ベースライン1 − ベースライン2: log loss +0.0036（−0.0015 〜 +0.0081）
- 推定器は0.05〜0.1帯をやや過大、0.1〜0.2帯をやや過小に推定する
- validでの選択の経緯: 離散特徴だけ（v1）→ scoreの区分を追加（v2）→ scoreの数値を追加（v3）。
  validの判断内AUCは0.681 / 0.683 / 0.684（ベースライン2は0.697）。L2はvalid log lossがほぼ一定

### データの再現性（公式generatorによる再生成）

Arenaの生成スクリプトの公式コマンド（`ca92451`、`LISJONG_SHANTEN_BACKEND=rust`、4 workers）で
200半荘を最初から生成し直し、`decisions.jsonl`（`d0805dbe…c0be5`）・`label_facts.jsonl`
（`84a324da…d52303`）・`manifest.json`（`e1a6f65e…d05b`）がbyte単位で一致することを
2026-10-03に確認した（約77分）。比較に使ったデータは、同じ生成関数を半荘ごとに途中保存する
一時wrapperで作ったもの。うち最初の4半荘はPython版のshanten backendで生成し、seed 931203を
Rust版で再生成して一致を確認した。

### 事後分析（testを見た後。選択済みのモデルは変えていない）

`posthoc`コマンドで、比較条件をそろえたベースライン2（構造的に安全な牌=0、残りをvalidの非安全牌で
校正）を加え、安全が確定していない牌だけの評価と、最安全牌の対比較を行った。この結果を受けて
特徴を変える場合、その最終評価には新しい保留データが必要である。

推定器 − 条件をそろえたベースライン2（半荘単位bootstrap、95%区間）:

| 評価範囲 | 分割 | log loss | Brier |
|---|---|---|---|
| 全候補 | test | −0.0034（−0.0066 〜 −0.0007） | −0.00060（−0.00109 〜 −0.00015） |
| 全候補 | valid | −0.0021（−0.0051 〜 +0.0007） | −0.00021（−0.00072 〜 +0.00028） |
| 非安全牌だけ | test | −0.0039（−0.0074 〜 −0.0008） | −0.00068（−0.00123 〜 −0.00017） |
| 非安全牌だけ | valid | −0.0024（−0.0058 〜 +0.0008） | −0.00024（−0.00082 〜 +0.00032） |

非安全牌だけの判断内AUCは、推定器 / 条件をそろえたベースライン2で test 0.640 / 0.643、
valid 0.639 / 0.656。

最安全と推定した牌の対比較（推定器 対 条件をそろえたベースライン2。同点は牌の集合として扱い、
ロン牌率は同点内の平均）:

| 分割 | 選んだ牌が異なる判断 | 両方安全 | 両方ロン牌 | 推定器だけ悪い | ベースラインだけ悪い | ロン牌率の差（推定器−ベースライン、95%区間） |
|---|---|---|---|---|---|---|
| test（2,150判断） | 216 | 200 | 0 | 10 | 6 | +0.0024（−0.0018 〜 +0.0068） |
| valid（2,415判断） | 234 | 228 | 0 | 6 | 0 | +0.0018（+0.0001 〜 +0.0042） |

ロン牌率の差の区間は、半荘を単位にしたpaired bootstrap（2,000回、固定seed）による。
参考として、元のベースライン2（安全牌の扱いをそろえない）との対比較では、選んだ牌が異なる判断は
test 572 / valid 578、推定器だけ悪い・ベースラインだけ悪いはtest 10 / 7、valid 6 / 1。
validとtestを合算すると、条件をそろえた比較で推定器だけ悪い16件・ベースラインだけ悪い6件だが、
これは参考記述にとどめる。

### 結論

- 既知安全牌の扱いを統一しても、testでは確率予測指標（log loss・Brier）に小幅な改善が残った。
  validでは同じ向きだが区間は0を含む
- 安全牌選択（最安全と推定した牌）の改善は確認できず、観測値はベースライン側が良かった
- 既存の打牌評価（古典的危険度score）を置き換える根拠はない
- 確率予測の改善は押し引きの改善を意味しない。押し引きには手牌価値や放銃時の失点も関わり、
  意思決定上の利益は未検証である
- 推定精度だけの結果であり、判断の質・強さの主張ではない
